# Research Agent Platform 产品规划 v0.7

2026-10-06 用户明确最终目标：**做成以个人为中心的 Personal Agent 系统，采用类似微信的交流方式；人与 Agent 在统一通讯录中共生，系统按任务难度和类型组织双方协作，持续形成获准的长期记忆、改进工作方式并主动跟进。** 本版将这一目标作为后续设计与开发依据。科研和实验室是首个验证场景，个人使用不以加入团队为前提。

当前工程事实以[统一状态](current-state.md)为准：联系人、自然聊天、显式创建、手动获准记忆、模型管理及有限外部文字服务接入已有基础；自动任务组织、行为记忆学习和个人主动跟进尚未形成真实使用闭环。当前部署API / worker57d059e、客户端aa3c0f1、contract0.17 / schema17保持；本次产品目标更新不改变运行软件。历史G/P1科研试点记录保留各自范围，不能用来证明最终Personal Agent目标已完成。分配规则见[任务分配与能力边界](task-allocation.md)，验证方法见[试点计划](validation-plan.md)。

## 1. 产品定义与本次修正

**每个人有一个持续陪伴的个人助理，了解本人获准的背景、偏好和正在做的事情。用户在聊天中提出目标，助理判断如何完成，调用或创建合适的Agent、组织真人协作，持续推进到交付，并在后续需要时主动跟进。人与Agent都以持续联系人身份出现。**

长期先围绕个人，再延伸到其联系人和协作网络；个人可以独立使用，也可以参加团队。科研是熟悉场景中的首个验证入口，不预先把跨行业扩展当作已成立的市场。从自己的科研小组开始验证论文、项目申请、工作材料、实习生协作、讨论与探索；研究方向暂不限定，交付形式由目标决定。

前台以置顶个人助理、通讯录、私聊和群聊承载。个人助理的对话同时承载日常交流、需求和跟进；协作单及任务状态按需展开。简单事情直接回复或执行，专项工作可交给专属Agent，复杂协作才创建任务群。用户也可以直接找任一联系人，群中日常交流不必逐次经过协调角色。通讯录统一呈现真人和Agent，包含发现、添加、档案、私聊和入群；Agent另有负责人、实际运行连接、角色、性格 / 工作方式及持续记忆。

添加联系人、邀请入群和接受任务承诺分别保存。记忆分为 Agent 负责人自己的私有记忆和指定会话的共同记忆；仅获准内容进入对应模型上下文，公开档案不包含私有记忆。能力介绍是成员声明，实际执行支持由运行服务、工具和既有权限决定。设定性格不改变材料访问权、任务承诺或操作确认。

后台复用任务分配、状态、时间、依赖和成果管理，增量建立个人记忆及持久跟进服务。聊天中的承诺、任务和成果由权威服务记录；Agent档案及记忆有稳定身份与版本，跨刷新、模型更换和任务持续存在。现有记忆由用户明确保存 / 维护，自动学习及主动跟进是本版目标而非上线事实。成员不必先建立项目、搭工作流或维护多个看板才能开始做事。

### 1.1 四层产品结构

| 层 | 产品职责 | 后台依据 |
| --- | --- | --- |
| 联系人与交流 | 真人与Agent共用通讯录、档案、私聊、群聊；个人助理持续存在 | 稳定身份、关系、资料和授权；IM负责消息与媒体送达 |
| 任务理解与组织 | 根据类型、难度和上下文选择直接处理、专项Agent或人与Agent协作 | 任务目标、可用能力、依赖、成员承接、运行状态和交付 |
| 长期记忆与个性化 | 记住本人习惯、偏好、工作方式、长期目标和经验，影响下一次决策 | 有来源、范围、版本、纠正与失效规则的记忆及相关检索 |
| 持续推进与改进 | 跟进等待、截止、变化和结果，反馈帮助下一次工作 | 持久事件 / 调度、执行回执、通知控制、反馈与能力版本 |

人与Agent共享联系人交互模型；真人是否承接由真人决定，Agent能否执行取决于所属人的授权和实际工具。个人助理协调上述各层，界面上的聊天文字由真实状态支持。

### 1.2 自动组织应怎样发生

用户说“想做一件事”后，助理先读取相关的获准背景，提取目标、交付标准和约束。任务类型与复杂度结合能力跨度、依赖步骤、信息缺口、需要人的判断、时间及用量确定，不能只按输入长度或一个分数决定。

1. 简单问答 / 已有能力可完成的短任务：个人助理直接处理，不必新增联系人或群。
2. 一项明确专业工作：优先复用匹配的已存在Agent；需要长期专属角色时自动整理设定、保存联系人并打开其聊天。只换名称不会获得新的工具能力。
3. 多阶段或多人工作：拆分交付与依赖，选取少量合适的人和Agent，给出分工并按获准范围建立任务群 / 安排。真人接受后才成为已承接；拒绝、受阻和能力不足反馈到协调流程。

自动化以用户已授予的范围为依据：常规工作可持续执行，超出授权或需要新的真人承诺时，把少量必要决定带回聊天。具体分级动作与撤销机制在工程批次中定义；本版不改变现有命令权限。聊天切换或关闭后，已承接工作仍由后台推进；重复请求、回执迟到及重启不能重复创建、派发或报完成。

### 1.3 长期记忆、主动跟进与持续迭代

个人长期记忆围绕稳定用户身份保存，供本人授权的助理与专项Agent按相关性使用；Agent自身工作经验、某段会话和任务共同记忆分别管理。模型上下文窗口只装载当前需要的记忆。公开联系人资料不包含私人行为档案；现有外部文字接入仍仅传当前消息，扩大范围需要单独实现。

形成记忆时区分用户明确表达、实际行为和AI推断：例如“我希望先看结论”是明确偏好，数次选择简短回复只能形成可纠正的候选。用户可以查看、修改、暂停学习和移除记忆；新的明确纠正优先，记忆注明来源 / 时间 / 适用范围。默认一次聊天中的偶然表达不会被当成永久性格结论。可在用户选择的学习范围中自动积累，不要求每条对话都确认一次。

主动跟进来自明确目标和真实事件：交付接近截止、任务受阻、等待回复、条件变化，或用户约定“之后帮我关注”。调度在服务端持久保存，不依赖打开网页或LLM记得时间。跟进回到对应私聊 / 群聊，可暂停、取消、合并及设置安静时段；没有变化时保持安静，已经完成的事项停止催问。

持续迭代包括对用户理解、匹配方式、工作策略及Agent能力版本的改进。采用“交付 → 用户反馈 / 真实结果 → 获准经验 → 下次应用 → 检查效果”的循环；过程保留可追溯版本。自动提取经验、更新提示与修改工具 / 代码分别验证，不能仅靠模型宣称自己已经升级。

v0.2 中“先进入项目、再选择智能体”和以能力作者共享为起点的流程，已被本版修正。项目仍可作为资料与相关任务的组织方式，但不是开始任务的前置条件。个人不愿分享自己的方法，不影响其领取、承担和完成任务。

2026-09-29 的修订明确三件事：产品第一阶段 P1 与工程 F1/G1 分开；保留用户选定的“对话中展开协作单”；先完成真实任务、少量公共能力与授权结论复用，完整能力市场和私人能力托管另行安排。第一阶段不因接项目而转成完整科研行政系统。

## 3. 为什么做，以及先服务谁

发起人已明确描述：同时有很多需要安排、参与或亲自完成的事情，缺少清晰的任务全貌与时间安排，复杂科研平台的入口和流程增加了使用负担。这是首批需求依据；其他成员是否有相同困难仍需观察。

| 需求 | 产品希望带来的变化 | 验证依据 |
|---|---|---|
| N1：事情零散，目标与节点尚不清晰 | 从一段不完整描述得到可修改的任务安排 | 整理所需时间、遗漏、重复任务和无依据的时间建议 |
| N2：不知道自己做什么、谁能参与、哪些可交给 AI | 在任务上下文中得到有理由的协作建议 | 建议被接受或修改的原因；成员是否实际承接；能力是否可用 |
| N3：安排后仍需不断催问和重新解释 | 任务、依赖、结果和下一步持续衔接 | 催问、重复交代、等待与交接投入是否下降 |
| N4：个人方法需要保护，共同能力又要复用 | 成员用自己的方式交付，公共能力自愿共建 | 私有内容不因协作泄露；公共能力被实际采用和维护 |
| N5：做完一次，经验难以帮助下一次 | 保留授权共享的依据与结论，分别改进公共和个人能力 | 下一次是否正确复用，错误是否减少，维护投入是否可承受 |

首批重点验证同时亲自工作并协调他人的博后、青年教师和项目负责人；研究生、助理与实习生应直接获得清晰要求、能力支持和方便交付。使用者、引入者和付费决策者可能不同。个人订阅、课题组付费、学校采购与标准产品加实施分别验证；科研人口、一个采购案例或内部满意度都不能直接证明市场规模。

首批角色包括任务发起人、承担者、参与者、验收人、公共能力维护者。一个人可兼任多个角色；由 AI 执行的任务也要有明确的人类责任人。研究者和实习生既可接任务，也可提出任务或建议重新定义问题。

平台价值需与参与者正在使用的聊天工具、文档和协作方式比较，包含组织、检查、返工、交接和维护成本。内部试用成功不直接证明市场规模或付费需求。

## 4. 两类能力与人的参与

| 类别 | 谁能使用 | 对团队公开什么 | 明确边界 |
|---|---|---|---|
| 公共能力 | 公布的使用范围内所有成员 | 适用任务、必要输入、交付示例、使用条件、维护者、版本和可用状态 | 共同可用不代表私有任务材料可共享，也不必默认公开源代码；本阶段指平台成员，互联网公开发布后续单独决定 |
| 个人私有能力 | 所有者，或其明确授权的使用者 | 默认不进入公共目录与其他人的匹配结果 | 不因承担公共任务、任务负责人身份或公共能力缺口而被强制披露、调用、复制或抽取为共享 Skill |
| 成员承诺的任务能力 | 成员接受任务后提供交付 | 自愿公开的专长、可投入时间、承诺和交付结果 | 不要求登记其所有私有智能体，也不要求披露完成工作的方法 |

公共能力优先覆盖基础、通用的工作，例如资料整理、通用检索、格式和一致性检查，具体是否可用以真实工具与任务验证为准。个人核心方法没有自动贡献到公共库的义务；缺少公开专长记录也不应阻止成员收到邀请或申请认领。

例如，一位成员可以公开说明自己能完成资料分析，但不公开自建智能体的名称、提示词、工具配置和内部执行记录。平台据其专长与意愿推荐人选；成员承接后，自行决定用哪些个人能力完成。

公共匹配只使用有权访问的任务上下文、公共能力和成员愿意公开的资料。个人工作中的匹配才可以使用本人私有能力。给发起人的方案不能通过推荐理由、日志、错误提示或能力缺口说明间接透露他人的私有能力。

每个人在自己的入口可以同时匹配公共能力与本人私有能力，发起人也一样。个人方案中使用了私有能力，不意味着完整方案可直接转发给团队；共同协作视图只展示需要他人知晓的交付与安排，私人执行方法留在个人视图。

任务验收需要约定的结果和必要依据。隐私边界保护个人方法，不免除成果可检查、来源可核对及协作中已承诺的交付要求。具体公开哪些内容，在承接前说清楚。

## 5. 用户实际经历的三个状态

### 5.1 表达需求

用户可以输入“我有一份科研项目申请书要写”，也可以一次说出几件尚未理清的事情。AI 利用有权使用的已有背景，只补问会影响计划的关键问题。允许暂时没有截止日期、负责人或完整材料。

系统先保留为草案。目标、硬性截止、估计投入和建议检查点分开表示；猜测不自动变成既定安排。任务可以关联已有项目，也可以从当前需求直接开始。

### 5.2 确认方案

在当前上下文中展开一份简洁的协作方案，重点说明：最终要得到什么、哪些事情要做、哪些由本人判断、哪些可由公共智能体承担、哪些拟邀请他人或开放认领，以及依赖、节点、能力缺口和必要用量限制。

用户可以用自然语言修改：“这部分我自己做”“先不要邀请别人”“给实习生留一个可尝试的部分”。每次修改更新同一份方案。建议人选、建议时间、已有承诺必须有明确区别。

公共匹配可以出现两种不同结果：“公共库缺少可直接调用的智能体”，或“已有成员愿意承担该结果”。后者不要求该成员把自己的方法贡献给公共库。

### 5.3 推进事情

确认方案后，后台生成或更新任务，按确认范围创建邀请、开放认领，并启动满足条件的公共智能体任务。重复确认不能重复建任务或重复发出邀请。成员未接受之前，不能表示其已承诺交付。

系统将需要补充、判断、承接或验收的事项带回相应成员的同一入口。正常进展以简短摘要呈现，详细任务结构按需展开。界面不要求用户逐个管理多个面板，也不能因界面简洁而隐藏失败、中断、超出用量限制或待人处理的状态。

成员可直接问“我这周能接什么”，获得少量符合访问范围、意愿、能力和可投入时间的任务；可认领、申请参与或拒绝。承接后可以使用公共能力、自有私有能力或平台外已有工具，按约定提交结果。

创建任务、查看进度和寻找可承接工作，采用同一入口下不同的受控回复组件。AI 选择合适的呈现结构，服务提供授权数据和操作回执；历史回复不代替当前状态。详见[按意图组织回复](design/adaptive-responses.md)。已有手工表单在真实 AI 接通前继续可用。

## 6. 任务分配是第一版的核心系统

任务分配包括四种方式：本人承担、指定邀请、开放认领、公共智能体执行。邀请与认领处理人的承诺，执行队列处理智能体运行，两者不能混为一谈。

每项可分配任务至少说明预期结果、验收标准、所需资料与访问范围。人类牵头者、参与者、验收人、依赖和时间信息逐步明确。一个任务可以有多人参与，但应有明确的牵头责任，不能因多人或多智能体参与而无人收尾。

系统需要处理并发认领、拒绝或退出、任务依赖、变更时间、转交、受阻、取消、提交成果、要求修改和验收完成。任务方案先确认再生效，已经发生的承诺与执行不能被新计划静默改写。完整规则及验收场景见[任务分配设计](task-allocation.md)。

前台简单，后台必须可靠。任务结果、人员承诺和真实执行状态应由确定的规则保存与更新，不能只存在于 AI 的对话文字中。

## 7. 能力缺口、创建与进化

现有软件支持个人模型 / 原实验室兼容配置、专属Agent四项资料与获准记忆、自然聊天、显式创建、公开人设导入及有限外部文字服务连接。完整私人工具托管、任意代码执行、Skill发布 / 试跑仍属于后续能力工程；能力资料与已接通的运行能力分别展示。

出现缺口时，用户可以选择自行承担、邀请合适成员、接入现有能力或创建新智能体。创建能力不应成为完成当前任务的强制前置条件。

用户可以说“把我刚才这套做法做成一个智能体”。平台帮助整理输入输出、必要资料、工具、示例和验证方法。个人新建能力默认私有；选择贡献公共能力时，需由所有者明确确认可发布的内容与范围，并去除私有资料和凭据。发布前验证可运行与可检查，保留版本和维护者。

能力进化来自真实反馈，但有明确边界：

- 公共能力根据获准共享的使用反馈和可公开样例改进，由维护者验证后发布新版本。
- 个人能力利用本人授权的反馈在私有范围内改进，不自动回流到公共能力库。
- 任务中共享的成果与结论用于已约定的协作范围；共享交付物不自动授权平台提取个人方法、训练模型或公开其内部过程。
- 重要判断修正保留原因，新版本不改写旧任务历史；可停用或回退不可靠的版本。

Personal Agent的长期目标包含持续迭代。当前先验证记忆提取 / 应用、匹配及工作策略的改善；工具与代码更新、模型训练是分别授权和验收的能力，未因这一目标更新而开放。

## 8. 最小版本范围与验收

R1—R8保留原科研协作目标，R9—R11补充Personal Agent核心要求；部分人类协作已在G1实现。原P1范围和历史状态见[第一阶段范围](phase-one.md)，新增主线见[路线图](roadmap.md)。不把整张表标记成已实现，各功能开放时分别验收。

| 编号 / 对应需求 | 目标要求 | 验收 |
|---|---|---|
| R1 / N1 | 自然语言需求与可修改方案，允许暂缺信息，不必先创建项目 | 用户从一句话得到能看懂的结果、分工与待确认项；建议不会成为虚构事实 |
| R2 / N2、N4 | 公共能力与成员匹配，个人范围内可使用私有能力 | 发起人只能看到授权的信息；成员不披露私人方法也能参与和交付 |
| R3 / N2、N3 | 方案确认、本人承担、邀请、认领、依赖与变更 | 重复确认、并发认领不会重复分配；邀请可拒绝；变更保留历史与承诺边界 |
| R4 / N3 | 后台执行、等待输入、受阻、取消、有限重试和用量约束 | 离开浏览器任务仍受管理；重启与失败状态真实；需要人的事项可返回同一入口 |
| R5 / N3、N4 | 提交、检查、要求修改、验收和成员交接 | 运行完成不等于交付被接受；检查人能核对必要结果与依据，无需查看私有方法 |
| R6 / N4、N5 | 任务资料与个人资料分开，权限、导出、访问收回和移除规则 | 接任务只获得所需材料；任务发起人无权查看他人的私人能力与记录；撤销后停止越权读取 |
| R7 / N5 | 授权共享的任务记忆；公共与个人能力分别维护 | 后续工作能复用正确内容；个人反馈不会被自动复制到公共库；能力更新经验证且可追溯 |
| R8 / N1、N3、N4 | 实验室 / 我参与的任务总览、人员安排与单任务详情，与对话共用任务数据 | 聚合也遵守访问权限；仅按实际承诺、执行、提交与验收更新；可用时间由成员提供，不按任务数量推断负荷或透露私人任务 |
| R9 / Personal Agent | 按任务类型与复杂度选择直接处理、复用 / 创建Agent及人机协作 | 简单任务不乱建群；真实能力不足明确；可修正分工，真人承接真实，重复组织不重复派发 |
| R10 / Personal Agent | 获准自动形成、检索、纠正和移除个人长期记忆 | 跨会话相关记忆确实影响工作；AI推断与用户表述分开，撤回与纠正后下一轮生效，其他人无法读取 |
| R11 / Personal Agent | 持久主动跟进及反馈驱动改进 | 离线 / 重启仍跟进，同一事件去重；静默 / 取消生效，完成后停止；后续任务展示实际复用效果 |

R9—R11是2026-10-06新增的核心目标，优先顺序见[路线图](roadmap.md)，其完整工程不标为历史P1已通过。主动跟进的最小持久调度纳入这一主线；更广泛文件格式、复杂匹配排序和外部市场随真实需要增加。网页保持聊天主入口，总览与任务详情按需展开，不要求重复维护数据。视觉历史见[界面图](design/README.md)，旧批次开发交接保留其受测范围。

## 9. 需要保留什么

| 内容 | 保存范围 |
|---|---|
| 共同任务 | 目标、方案版本、已确认的安排、成员承诺、当前状态、依赖、交付、验收和授权共享的判断理由 |
| 公共智能体执行 | 在任务授权范围内的输入输出、公共能力版本、用量和必要运行记录 |
| 个人执行方法 | 私有能力配置、私人笔记、内部执行过程及私人反馈；由本人控制，默认不进入共同任务记录 |
| 组织知识 | 获准共享的原始资料、成果、确认过的结论和适用范围；候选与已确认判断分开 |

需要解释“为什么改变了共同任务安排”，不等于必须披露“某成员私下具体怎样完成工作”。当验收需要某项方法或复现资料时，应事先写进任务约定，由承接者决定是否接受。

应用权限与运维人员直接读取服务器的能力是不同边界。部署时必须明确实际私有性保障；如要求运行环境管理员也无法接触个人方法，需要单独隔离的个人执行方式，不能仅靠隐藏界面宣称满足。

## 10. 阶段与成功依据

| 阶段 | 重点 | 通过依据 |
|---|---|---|
| M0 | 用真实任务验证简洁入口和协作方案 | 发起人看懂分工，成员愿意承接，结果与时间约束明确；不要求先分享私人能力 |
| M1 | 实现任务分配与能力边界，再接上同一入口、总览和真实执行 | 按 P1 交付 R1—R8 的必要部分；人、公共智能体、个人自主完成三种方式衔接；私人方法可留在平台外 |
| M2 | 持续组内使用 | 减少漏事、催问、重复解释与交接负担；非开发成员下一次主动使用；结果可用且维护成本可承受 |
| M3 | 向相似课题组扩展 | 无需逐组重写核心分配逻辑；公共能力可复用；个人能力边界被尊重；商业模式另行验证 |

公共能力增长与外部作者生态是后续观察项，不能把强迫成员交出自己的方法当成平台成功。首批验证同时观察协调成本、成果质量、承接意愿、私有性与自然重复使用。

当前仍需补齐首批真实任务、参与者、可交付标准及实际访问范围。公开市场、支付、完整人事与财务系统、跨组织自主调度等不在首版范围。工程状态与依赖见[架构说明](architecture.md)及[迁移记录](migration.md)。
