# 科研微信：协作链条与页面完善

2026-10-04，起点 `95c838b`。用户要求继续以自己的科研微信逻辑为主，完善逻辑链条和前端页面。保留统一真人/Agent 联系人、唯一置顶需求协调入口、人和 AI 的任务群。此次不安装 ANet、不随开发部署或推送。

## 本轮范围

- 固定需求入口给出需求、交付、验收和成员安排的使用提示及可编辑需求模板；模板只填入草稿，用户发送后才请求 AI。
- 群内常驻任务摘要和可展开的协作面板，读取已有授权任务、承接、运行、交付与验收记录；展示当前阶段、成员加入、承接者、验收要求和下一步。
- 分开解释添加联系人、接受群邀请、接受任务承诺、授权材料、确认 AI 执行与验收；普通聊天和 @ 提及不隐式派发任务。
- 合并目前同一请求的“问 AI / 让助理安排”，让群内发送方式只有明确的普通聊天或请求所选 AI 回复/提出安排。安排仍需确认具体范围。
- 任务完成以服务任务状态/指定交付版本验收为准；运行成功、候选成果、加入群或接受邀请不算完成。状态摘要不能猜测权限不可读的任务。
- 优化聊天、通讯录与移动页面的信息层级、留白及主要操作；轮询保留草稿、面板展开状态，失败保留输入。

## 分工

总控负责授权任务到页面的事实投影 `chat-workflow.ts`、适配器接线和独立集成验证。前端负责 chat-view、CSS、联系人和必要前端测试。后端审核并修补本轮协作链条的实际权限/状态问题，保持现有契约和数据库兼容，只有发现具体缺陷时改变服务行为。

前端使用 `chat-workflow-types.ts` 的 `ConversationWorkflowView`；`ConversationView.workflow` 是可选字段。TaskView 的 actionLabel/href 只导向现有授权任务详情操作，不用纯前端改变任务状态。后端和前端沿用独立克隆，均从总控起点建工作分支，以提交整合。

## 验证

重点验证需求模板不自动发送、普通 @ 不调用模型、群员加入不承诺任务、待接单/阻塞/返工/待验收/完成的真实投影、受限摘要不泄漏详情、多任务不同进度、轮询保留草稿/面板以及桌面/320px 可操作性。共享服务改动运行全量 CI；供应商真实模型调用单独报告。

## 桌面方向

用户在本轮明确桌面端参考 **OpenIM**，其联系人、私聊和群聊结构更贴近科研微信；OpenIM Electron 的窗口和打包实现作为后续桌面主要参考，共用我们的科研业务与服务接口。ANet 仅参考分布式 Agent 执行节点。此轮讨论尚未产生桌面构建或安装包，不把网页验收记作 Electron 验收。

## 实际整合

当前实现保留契约 **0.12.0**、聊天协议 **1.2.0**、迁移 **014**。群协作由总控 `chat-workflow.ts` 投影已有服务事实：只读取群内且当前用户可读的 taskIds；已接受的 assignment 才显示承接者；最新交付 revision 与任务状态决定验收和完成。授权摘要只显示服务明确给出的信息。权限动作导向现有任务详情，不在页面中制造任务状态。

前端新增固定需求入口、三个仅填草稿的模板、群协作摘要和面板、承接/验收要求/下一步及现有详情入口。普通聊天中的 @ 不调用模型；请求 AI 回复和提出安排使用同一明确模式，具体安排仍需查看范围并确认。首次使用说明同步更新。

后端复用实际任务命令的邀请与运行预检，避免展示必然失败的可确认建议；提案产生、发布、投影和确认继续重查权限及版本。具体边界和 63 项 HTTP/worker 专项见[后端记录](chat-workflow-backend.md)。

浏览器验收另发现并修复两处具体问题：群邀请展开范围被轮询折叠；390px 同时展开群成员与协作面板时发送按钮被挤出视口。邀请现在保留展开范围并绑定当前动作；窄屏的成员与协作内容独立滚动，输入区保留可用空间。截图和运行数据保留在 Git 外。
