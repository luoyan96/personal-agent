# 账号输入与注册错误修复

本地基线 `3d3ccb67eb52a14364dc46b9509737e3f0b6674a`。本轮只修改共享契约和 API/账号维护；未读取线上截图中的邀请码或密码，未线上注册、部署或推送。

## 输入规则

- 契约与包版本为 **0.13.1**，导出 `AccountUsername`、`AccountPassword`、`RegistrationCode`；OpenAPI 和合成示例同步导出。
- 用户名只 `.trim()` 首尾空白，之后保留原 ASCII 字母/数字/下划线/短横线的 1–100 字符规则和大小写区分。登录、注册、维护建号与合成测试建号一致。不会删除中间空白或零宽字符，不做 NFKC 或大小写合并；截图本身不能证明具体隐藏字符。
- 注册邀请码只去除首尾空白，长度/字符规则、散列查找、当前有效性、名额和负责人开通授权保持原逻辑。
- 密码至少 8 个字符，去除独立 256 字符上限，无复杂度要求且不 trim。散列、验证码之外的角色/实验室字段拒绝、Origin/CSRF、登录限流、注册 KDF 并发/幂等和凭据重置撤销会话保持原逻辑。
- 整体输入上限保留：注册 HTTP 8192 字节；一般 HTTP 1048576 字节；维护 CLI stdin 16384 字节。

## 错误呈现

服务原本已将 HTTP 错误封装为 `error{code,message,requestId}`，没有把原始 Zod 错误当响应。前端预解析仍可能显示 Zod 的 message，客户端修复由前端负责。本轮在服务端增加封闭白名单的账号字段中文提示；不把输入值、issue JSON、正则、SQL 或异常信息拼接进消息。维护命令解析失败只抛 `INVALID_INPUT`，CLI 保持原脱敏诊断。

## 本地验证

`registration.spec.ts` 使用独立生产模式配置、空 SQLite 与合成邀请码，并实际启动 loopback HTTP 服务，通过 fetch 验证：

- 7 字符拒绝且不消费邀请码，8 位纯数字注册/登录成功。
- 首尾空白用户名和邀请码成功注册；持久 username 已规范化，带空白登录成功且实验室不变。
- 相同幂等键的规范化重试不多用名额，规范化后的重名仍冲突。
- 中间空格、零宽字符、全角同形字拒绝，注册和登录返回中文错误且不回显输入或 Zod 内核。
- 300 字符密码注册/登录成功；首尾空格密码只按原值验证；9000 字符注册请求仍被整体限制以 413 拒绝。
