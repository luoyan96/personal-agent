# 定时任务与重复提醒

2026-10-07 本地实现，分支 `feature/recurring-agent-tasks`，Windows 候选版本 0.4.0。共享契约 0.20.0、聊天协议 1.9.0、显式迁移 019。云端是否更新以 `docs/current-state.md` 的部署记录为准。

## 用户怎么用

- Windows0.5.0“工作台 → 定时任务”或“左下角设置 → 定时任务”：新建一次、每天或每周的安排；每周可选多个星期。0.4.0历史候选使用独立导航入口。
- 可以选择“提醒我”，或者让自己的站内 Agent 到点处理指定文字任务。选择执行 Agent、首次时间、时区、每次预算和安静时段，保存后可以关闭客户端。
- 也可以向个人助理或自己的站内 Agent 说“每天上午九点提醒我整理待办”“每周五下午六点帮我总结最近的聊天”。明确的时间指令直接保存安排；缺少时间会询问。问句、举例和否定指令不创建安排。自然语言执行指令使用当前聊天的 Agent，不自动选择其他联系人。
- 查看下次时间、最近一次状态和分页运行记录，修改、暂停、恢复、结束或取消。暂停和修改会栅栏尚未完成的旧运行；恢复从下一次未来时点开始。

到期由云端 worker 处理，消息写入原有权威聊天库后沿 OpenIM outbox 投递。未发出、已写入、IM 已接收、投递待核对分别展示。没有新增 Windows 系统通知；退出客户端后可以执行的前提是 API、worker 和相关云服务持续运行。

## 执行范围

定时 Agent 使用本人当前模型设置、Agent 档案、获准偏好和该 Agent 私聊中可用的近期文字。沿用既有聊天历史范围及预算，不能把“最近聊天”解释为无限历史。每次默认 4000 Token / 90 秒；界面可设 1000–16000 Token / 10–120 秒。实际模型用量与不确定用量保留既有记录。

不新增网页检索、外部 Agent 调度、通用工具、本地文件夹后台读取或自动改文件。云端不能访问退出后的本机目录。模型不可用或同一聊天正在处理其他消息时，该次记录真实跳过原因；不打断用户手上的聊天。每人最多 50 个未结束安排，继续遵守现有 5 个活跃模型轮次限制。

## 调度和持久化

- `personal_followups` 保存当前安排；019 只新增 `personal_followup_runs` 和索引，既有 18 迁移的 checksum 与旧数据不改。旧文档默认一次性、无 Agent 执行，历史已发提醒不重发。
- 每次发生以 `(followup_id, scheduled_at)` 唯一约束；发生记录、权威消息、模型轮次和推进下一次时间在同一 SQLite 事务内写入。重启与重复 worker 不生成第二份同一次发生。
- 以明确时区的日历时点重复；夏令时不存在或出现两次的时点跳过，不偏移或重复执行。多次逾期合并处理一次，随后推进未来时点，避免恢复后集中补跑。
- 安静时段推迟处理。失败、超时或用量不确定不自动重试模型；下一次正常发生仍有独立记录。缺少有效权限会停止安排，不向失去权限的聊天发通知。
- 当前授权、联系人归属、任务 ACL、模型配置和已有聊天栅栏继续检查。服务消息仅在准确匹配本人已保存安排、发生记录、轮次、消息和 Agent 时可以作为模型输入，普通 service 消息不会因此获得执行权。
- 修改、暂停、结束和取消令未完成定时轮次取消并增加 durable fence；迟到结果不能提交。运行结果结算与失败通知单独持久化，不重复调用模型。隔离恢复工具暂停所有 active 安排，包括已有发生记录的重复任务。

## 验证与部署

专项覆盖真实 HTTP / SQLite 持久化、旧库 18→19、自然语言时点、DST、逾期合并、重复派发、实际 ChatWorker / 合成 ModelCall、失败通知、取消迟回复、模型缺失、聊天忙碌、跨账号拒绝、版本冲突与分页。客户端使用实际生产导航 / 表单 / 记录组件在隔离 Electron 22 内验收，API / SDK 明确合成；不调用用户模型、账号或资料。

证据保存在 Git 外 `.runtime/recurring-agent-tasks-20261007`；包括初次失败报告和后续修正。初次完整 CI 的旧 migration / contract 期望值失败已经同步，546 项工程测试通过；生产入口旧 018 断言修正后 2 项通过，后续 B0 进程与 Web 生产隔离门禁通过。实际完整 CI 退出结果、桌面交互与安装包门禁各自记录，不能把合成检查当成真实云端模型验收。

发布必须成对更新 API / worker：先在隔离库核对 019，然后停本项目写入者、备份当前数据、执行正式迁移及完整性 / 旧行核对，再启动固定源码的新 API / worker。记录 `/health/ready` 的 0.20.0、迁移 19、源 / 镜像及服务状态。不要重新 provision 密钥或启动 bootstrap，不改变其他网站与数据库端口。

数据库升级后不能直接启动只认识 schema18 的旧镜像，也不能用旧快照覆盖新增聊天 / 用量。需停止写入者、保留当前数据库并栅栏定时轮次、暂停安排，再部署能识别 schema19 的兼容修复版本。尚未实际完成云端迁移或回退演练时必须明确记录；公共桌面更新资产应在匹配后端可用后发布。
