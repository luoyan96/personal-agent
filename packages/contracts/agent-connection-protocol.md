# Agent import and external connection v1

Contract0.17 / chat1.6. Every response has the ordinary `{data:...}` wrapper.

- `importAgentProfile`: POST `/api/v1/chat/agents/import`, body `{format:"research-agent-profile/v1",profile:{displayName,introduction,capabilityDescription,personality}}`; response `{data:{contact,conversation,reused,mode:"profile_only"}}`. Public profile only: no credential, memory, endpoint, tool or execution authority. Exactly matching owned local specialists may be reused. The canonical direct is already saved; IM readiness is a separate bridge operation.
- `exportAgentProfile`: GET `/api/v1/chat/agents/{id}/export`; owner specialist only, response `{data:{format,profile}}`.
- `agentConnection`: GET `/api/v1/chat/agents/{id}/connection`; owner specialist only, `{data:{connection:null|AgentConnection,version:0|number,lastProbe:null|AgentConnectionProbe}}`.
- `updateAgentConnection`: POST same path, `{expectedVersion,protocol:"chat_completions",endpoint,model,enabled,allowAcceptedContacts:false,apiKey?,removeApiKey?}`. Version0 creates the initial binding. Credentials are encrypted and only `hasApiKey` is returned. Changing endpoint requires a new key or explicit removal while disabled. Configured/enabled does not mean the remote service has been tested.
- `disconnectAgentConnection`: POST `/connection/disconnect`, `{expectedVersion}`. Remove the remote binding/key; retain monotonic version. New local chat again uses the sender model. Existing external turns never silently switch to it.
- `probeAgentConnection`: POST `/connection/probe`, `{expectedVersion}`. Explicit owner-funded synthetic check. `{data:{contactId,version,status:"passed"|"failed"|"uncertain",failure:null|ExternalAgentFailure,usage:null|ModelUsage,at}}`. An uncertain receipt is saved before network I/O; exact retries cannot trigger a second charge after a crash. Recheck owner/session/version after I/O.

Mutations require session, Origin, CSRF and `Idempotency-Key`. Public `Contact.agentRuntime` appears only for configured external Agents: protocol, HTTPS `serviceOrigin` only (no path/key), `scope:"current_message"`, `credentialPayer:"agent_owner"`, caller/share policy, `requiresConsent:true`, probe verification. Platform Contacts and ordinary persisted messages/turns preserve the previous strict shape. Older clients must refresh before using external contacts.

Every external `agentChatMessage` requires `externalConsent:true` for that specific message, an owned specialist or accepted relationship and the owner's explicit `allowAcceptedContacts`. Only that current text is sent; no history, memory, files, profile, task, internal account/contact ID or SDK metadata. The external configuration owner's service account pays. No fallback or automatic retry. Attachments return `EXTERNAL_FILES_UNSUPPORTED`; advanced arrangement returns `EXTERNAL_SCOPE_UNSUPPORTED`; missing consent returns `EXTERNAL_CONSENT_REQUIRED`.

External v1 is an HTTPS443 OpenAI-compatible **chat-completions wire format**, not the OpenAI API or A2A. Full endpoint ends in `/chat/completions`, no URL credentials/query/fragment. All resolved IPs must be public; the connection pins an approved address and validates the original host's TLS identity. No redirect or environment proxy. Response<=100KiB, deadline<=90s, default total budget4000, no tools/tool_calls. Text/usage/finish are validated before saving; unknown usage and truncated output do not become replies.

Protocol references: [chat-completions reference](https://developers.openai.com/api/reference/resources/chat/subresources/completions/methods/create); [A2A1.0 specification](https://a2a-protocol.org/v1.0.0/specification). A2A discovery/tasks/streaming/cancellation are not implemented. A service must expose this supported wire format; arbitrary existing Agents are not automatically compatible. Tests use local synthetic HTTPS services, not vendor credentials or actual remote capability claims.

Migration017 adds the private binding table without rewriting old rows. Restore disables external bindings and fences old work. Old code refuses a schema17 database; rollback/forward recovery must be planned by the operator while preserving new user records, not assumed to be a code-only rollback.
